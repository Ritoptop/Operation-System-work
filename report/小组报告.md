## 摘要（约 150 字）

本组以「银行家算法拒绝请求是否意味着死锁」为问题，在 1–4 个进程、1–3 类可重复使用资源、请求串行且无抢占的边界内，建立安全性检查与当前请求归约两套独立判定。三类案例分别得到安全、不安全但未死锁、实际死锁三种结果，说明拒绝仅表示试分配后无安全序列，死锁必须由归约停滞确认；结论仅适用于该离散模型。

## 1. 问题与假设（约 0.5 页）

### 1.1 研究问题

银行家算法拒绝一次请求，是否表示系统已经死锁？最大可能需求、尚需量与当前实际等待，分别影响什么判断？

### 1.2 六条初始假设

| 成员 | 初始假设 | 理由 | 核验结果 | 证据 |
|---|---|---|---|---|

| 杨俊嘉 | 请求被拒绝时应把该请求写入 `requests[i]` 作为等待记录 | 直觉上被拒的请求会转为等待状态 | 修正：拒绝时状态逐位不变，`requests` 保持原样；仅授予成功才清除 `requests[i]` | `docs/model.md` §4；`src/core/request.ts`；`core.test.ts`「试分配后不安全返回 `UNSAFE_AFTER_TRIAL` 并回滚」 |

### 1.3 假设汇总

六条假设中，1 条被推翻、4 条被修正、1 条被支持。被推翻的是“拒绝即死锁”：`unsafe_01` 中 P0 的请求被拒，但归约仍可按 `P0 → P1 → P2` 全部完成，这是区分“不安全”与“死锁”的关键证据。四条修正集中在实现细节：`work` 累加的是 `allocation`、拒绝不写入 `requests`、等待环不是死锁的充分条件、`available` 应由守恒关系派生。被支持的是独立手推结论与程序一致。

## 2. 方法与模型（约 1 页）

### 2.1 模型边界

- 进程 1–4 个，资源类型 1–3 类，数量为非负整数。
- 资源可重复使用，用完可释放；不考虑抢占与故障。
- 请求串行处理，一次一个；不计管理开销。
- `max` 是进程声明的最大总需求，不是运行时事实。

### 2.2 五套数据与派生量

| 符号 | 含义 | 说明 |
|---|---|---|
| `total` | 资源总量 | 固定 |
| `available` | 当前可用量 | 随分配/释放变化 |
| `allocation` | 当前分配 | 已持有 |
| `max` | 最大需求 | 银行家算法的假设 |
| `need` | 尚需量 | `max − allocation`，派生 |
| `requests` | 当前等待 | `null` 表示未阻塞 |

### 2.3 请求处理与三类拒绝

一次请求按固定顺序处理：输入校验 → `request ≤ need` → `request ≤ available` → 试分配 → 对试分配后的状态做安全性检查 → 安全则提交，不安全则回滚。前两步分别对应 `EXCEEDS_NEED` 与 `EXCEEDS_AVAILABLE`；第三步失败对应 `UNSAFE_AFTER_TRIAL`。三种拒绝都必须保持状态逐位不变，试分配结果只保留在 `trial` 供对比；授予成功才清除该进程原有的等待记录。

| 拒绝码 | 含义 | 是否改变状态 |
|---|---|---|
| `EXCEEDS_NEED` | 超过尚需量 | 否 |
| `EXCEEDS_AVAILABLE` | 当前可用量不足 | 否 |
| `UNSAFE_AFTER_TRIAL` | 试分配后无安全序列 | 否（已回滚） |

### 2.4 安全性检查

`work` 初始化为当前 `available`，`finish` 全为假。每轮按进程编号升序，找第一个 `need ≤ work` 的未完成进程；找到则标记完成、记入序列，并执行 `work += allocation`（回收已持有量，不是 `need` 或 `max`）。找不到候选即停止，输出停在第几步、哪些进程的哪个资源不满足。全部完成则安全，序列即推进顺序；平局规则保证结果可复现，但不表示安全序列唯一。

### 2.5 实际死锁的归约判定

归约只看 `requests`、`allocation`、`available`，不使用 `max`。`requests[i] === null` 视为无阻塞，可直接推进；否则要求 `request ≤ available`。推进时先 `available -= request`，进程完成后释放全部持有：`available += allocation + request`。反复执行到没有可推进进程；若仍有进程带非空请求，则这些进程为 `stuck`，判定实际死锁。等待边只用于解释，多实例下环是必要非充分条件。

### 2.6 为什么安全性与死锁必须分开

安全性检查使用 `max` 假设，问的是「是否存在一种让所有进程完成的顺序」，它是面向未来的保守判断；死锁判定使用当前实际请求与持有，问的是「现在是否谁也动不了」，是对当前状态的判断。前者可能把尚未发生的等待算进去，后者完全不看最大需求。因此安全一定不死锁、死锁一定不安全，但不安全可能尚未死锁；`unsafe_01` 就是这种状态。两套判定必须分栏展示，不能用同一个标签。

## 3. 关键实验（约 1.5–2 页）

### 3.1 三类状态基线

| 案例 | 安全性 | 实际死锁 | 关键轨迹 | 证据 |
|---|---|---|---|---|
| `safe_01` | 安全 | 否 | 安全序列 `P1 → P3 → P0 → P2` | `evidence/exports/safe_01_20261126.json` |
| `unsafe_01` | 不安全 | 否 | 归约 `P0 → P1 → P2` | `evidence/exports/unsafe_01_20261126.json` |
| `deadlock_01` | 不安全 | 是 | 等待环 `P0 → P1 → P2 → P0`，stuck 为全部 | `evidence/exports/deadlock_01_20261126.json` |

### 3.2 安全序列人工核对

以 `safe_01` 为例：`total = [10,5,7]`，`available = [3,3,4]`。先由 `need = max − allocation` 得 P0 `[7,4,3]`、P1 `[1,2,2]`、P2 `[6,0,0]`、P3 `[0,1,1]`。按编号升序取第一个 `need ≤ work` 的进程，完成后执行 `work += allocation`。

| 步骤 | work（前） | 满足 `need ≤ work` 的进程 | 选中 | 选择依据 | work（后） |
|---|---|---|---|---|---|
| 1 | [3,3,4] | P1、P3 | P1 | P1 与 P3 均满足，取编号最小 | [3,3,4] + [2,0,0] = [5,3,4] |
| 2 | [5,3,4] | P3 | P3 | P0、P2 的 need 仍超过 work，仅 P3 满足 | [5,3,4] + [2,1,1] = [7,4,5] |
| 3 | [7,4,5] | P0、P2 | P0 | 两者均满足，取编号最小 | [7,4,5] + [0,1,0] = [7,5,5] |
| 4 | [7,5,5] | P2 | P2 | 仅剩 P2 | [7,5,5] + [3,0,2] = [10,5,7] |

手算结论：4 步完成全部进程，安全序列为 `P1 → P3 → P0 → P2`，与页面轨迹及 `cases/safe_01.json` 的 `expected.safeSequence` 完全一致；每步 `work` 单调不减，终值等于 `total = [10,5,7]`，满足模型不变量。

### 3.3 同一请求的双路径对比

| 路径 | 操作 | 结果 | 状态是否改变 | 说明 |
|---|---|---|---|---|
| 直接分配 | `safe_01` 中 P0 请求 `[0,3,0]`，不做安全性检查直接分配 | `available` 从 `[3,3,4]` 变为 `[3,0,4]`，P0 分配从 `[0,1,0]` 变为 `[0,4,0]` | 是 | 新状态在 `work = [3,0,4]` 下无进程满足 `need ≤ work`；当前无等待，故尚未死锁 |
| 银行家检查 | 同一请求，先试分配再检查安全性 | `UNSAFE_AFTER_TRIAL`，拒绝 | 否 | 试分配只保留在 `trial`，状态回滚到安全状态 |

拒绝的依据是「试分配后不存在安全序列」，不是「系统已经在等待」。直接分配后虽然当下没有死锁（所有 `requests` 为 `null`，归约可全部推进），但状态已经不安全；银行家算法在 `max` 假设下不允许这种可能走向死锁的分配。这正说明「不安全」与「死锁」是两层判断：拒绝是预防，死锁是现状。

### 3.4 拒绝原因三分类

三条记录均来自导出 JSON，操作前后状态快照逐位相同：

- `EXCEEDS_NEED`：`deadlock_01` 中 P0 请求 `[0,2,0]`，其 `need = [0,1,0]`，B 分量超限，第一步拒绝。
- `EXCEEDS_AVAILABLE`：同一案例中 P0 请求 `[0,1,0]`，满足 need，但 `available = [0,0,0]`，第二步拒绝。
- `UNSAFE_AFTER_TRIAL`：`unsafe_01` 中 P0 请求 `[1,1,0]`，前两步通过，试分配后 `available = [0,0,0]`、无安全序列，回滚。

证据：`evidence/exports/deadlock_01_20261126.json` 的前两条请求记录，`evidence/exports/unsafe_01_20261126.json` 的试分配回滚记录。

### 3.5 释放后的复检

在 `deadlock_01` 中让 P0 释放已持有的 `[1,0,0]`：释放前 `available = [0,0,0]`，实际死锁为是，stuck 为 `P0、P1、P2`；释放后 P0 分配归零、`available = [1,0,0]`，归约按 `P2 → P1 → P0` 全部推进，死锁判定变为否。安全性也需重算：`work` 从 `[1,0,0]` 开始，P2 完成后为 `[1,0,1]`，P0 完成后仍为 `[1,0,1]`，P1 完成后为 `[1,1,1]`，安全序列 `P2 → P0 → P1`，终值等于 `total`。结论：释放会同时改变安全性检查与实际死锁判定的输入，必须重新检查，不能沿用释放前的结论。证据：`evidence/exports/deadlock_01_release_20261126.json`。

### 3.6 反例与边界

三个边界实验均先预测再运行，结果与预测一致：

1. **修改 `max`**：在 `safe_01` 把 P0 的 `max[B]` 从 5 改为 6，预测 `need[B]` 增大、安全序列消失。实际安全性变为不安全，停在 `work = [10,4,7]`，P0 尚需 `[7,5,3]`，B 分量 5 > 4。
2. **修改当前请求**：在 `deadlock_01` 把 P0 请求改为 `null`，预测 P0 先完成、死锁解除。实际归约顺序 `P0 → P2 → P1`，死锁判定为否。
3. **增加进程**：在 `deadlock_01` 增加 P3（分配 `[0,0,0]`、最大需求 `[1,1,1]`、无请求），预判它可直接推进但不增加可用量。实际 P3 完成，`available` 仍为 `[0,0,0]`，P0–P2 仍 stuck，死锁保持为是。

差异与原因：`max` 只影响安全性检查；当前请求只影响死锁判定；没有资源持有的进程不改变等待关系，因此不会凭空打破死锁。

## 5. 结论与局限（约 0.5 页）

### 5.1 结论

- 银行家算法拒绝请求只说明试分配后不存在安全序列，不等于系统已经死锁。
- 安全状态一定不死锁；死锁一定不安全；不安全状态可能尚未死锁。
- 安全性依赖 `max` 假设，死锁判定依赖当前实际请求与持有，两者不能互相替代。
- 资源释放后必须重新检查，状态可能从死锁回到可推进。

### 5.2 局限

- `max` 是声明值，不是运行时事实；安全性判断是保守的。
- 模型不支持抢占、故障、多请求并发与真实内核调度。
- 进程与资源规模很小，有限案例不能证明算法的普遍性质。
- 导出证据来自离散模拟，不代表真实存储或内核行为。
