# 模型交互记录 L3：请求与释放表单的状态串扰

- 记录编号：L3
- 工具与模型：Trae Code Agent（模型标识 DeepSeek-V4.1-Flash）
- 日期：2026-11-26
- 背景：实现「请求与释放」面板时，模型第一次给出的组件只维护一个 `processId` 下拉框，请求与释放共用。
- 记录性质：由本项目会话整理；这是模型中真实出现的实现遗漏，修复过程有代码与操作记录。

## 实际提问

> 请实现请求面板和释放面板：可以选择进程、输入资源向量，提交后展示结果，并在请求被拒绝时显示试分配前后对比。

## 模型关键回答

> 首次实现中，两个表单共用同一个 `processId` 状态：在请求区把进程切到 P1，释放区的进程也一起变成 P1；反之亦然。模型当时认为「同一个页面只操作一个进程更简单」，没有考虑两个表单是独立操作。

## 学生判断

- 结论：修改
- 理由：请求与释放是两次独立操作，共用状态会让操作对象被另一次选择悄悄改写，属于可复现的交互缺陷。浏览器实测时发现切换请求进程后，释放进程同时变化。

## 验证证据

- 案例编号：`safe_01`
- 手工推演：在请求区选择 P0 并提交 `[1,0,0]`；再到释放区选择 P1，请求区的进程不应随之改变。
- 程序轨迹：修复前两处下拉框联动；修复后拆成 `requestProcessId` 与 `releaseProcessId`，互不影响。
- 证据文件位置：`src/components/RequestPanel.tsx`（两个独立状态）；浏览器操作记录见本报告 3.6 与个人分析 05。

## 核验后结论

- 实际结果：修复后分别选择 P0、P1，提交请求与提交释放均作用于各自进程，页面结果与核心函数返回值一致。
- 认识变化：模型给出的「简化」在单表单场景成立，在多表单页面不成立；界面状态必须按操作独立建模。
- 成立条件与局限：该修复只解决前端状态隔离，不改变核心算法；若以后增加更多操作面板，需要继续检查是否共享了同一份选择状态。
