# 模型交互记录 L2：请求处理顺序与三类拒绝

- 记录编号：L2
- 工具与模型：Trae Code Agent（模型标识 DeepSeek-V4.1-Flash）
- 日期：2026-11-26
- 背景：实现请求处理前，组内对「先查尚需量还是先查可用量」以及「被拒绝的请求要不要记入 `requests`」有分歧。
- 记录性质：由本项目会话整理；提问保留组员原意，原始截图由组员在提交前补充。

## 实际提问

> 一次资源请求的处理顺序应该怎样固定？如果请求被拒绝，是否应把它写进 `requests[i]`，表示进程正在等待？

## 模型关键回答

> 顺序应为：输入校验 → `request ≤ need` → `request ≤ available` → 试分配 → 安全性检查 → 提交或回滚。前两步的拒绝原因必须分开：超过尚需量是违反最大需求承诺，可用量不足是当前暂时不能满足，二者不能合并成「资源不足」。被拒绝的请求不写入 `requests`，因为本模型的 `requests` 表示案例给定的当前阻塞请求；拒绝不应改变状态。只有请求被授予时，才清除该进程原有的等待记录。

## 学生判断

- 结论：修改
- 理由：组内初稿原想「拒绝就把请求记入 `requests`，方便后续推进」，这等于把银行家拒绝误当成进入等待。模型建议与「拒绝不改变状态」的不变量一致，采纳模型顺序，并修改初稿。

## 验证证据

- 案例编号：`deadlock_01`、`unsafe_01`
- 手工推演：`deadlock_01` 中 P0 请求 `[0,2,0]` 超过 `need = [0,1,0]`；请求 `[0,1,0]` 满足 need 但 `available = [0,0,0]`；`unsafe_01` 中 P0 请求 `[1,1,0]` 通过前两步，试分配后无安全序列。
- 程序轨迹：三条拒绝分别显示 `EXCEEDS_NEED`、`EXCEEDS_AVAILABLE`、`UNSAFE_AFTER_TRIAL`，前后状态逐位相同。
- 证据文件位置：`evidence/exports/deadlock_01_20261126.json`（前两条拒绝）、`evidence/exports/unsafe_01_20261126.json`（试分配回滚）；`src/core/request.ts`；`src/core/core.test.ts` 请求处理相关用例。

## 核验后结论

- 实际结果：与模型回答一致；拒绝时 `requests` 保持原样，试分配状态仅保留在 `trial` 字段供对比。
- 认识变化：确认「拒绝」不是一种等待状态，而是三种不同原因导致的「状态不变」。
- 成立条件与局限：该顺序依赖 `max` 已知且请求串行；若允许多请求并发或抢占，拒绝后进程的等待语义需要另行定义。
