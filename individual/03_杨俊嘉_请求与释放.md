## 1. 我最初怎样判断，为什么

我最初认为：请求被拒绝后，应该把这次请求写入 `requests[i]`，表示进程「正在等待」，这样死锁判定就能看到它。理由是等待中的进程在现实里确实会留下请求记录。这个想法把「银行家拒绝」和「进程进入等待」混在了一起。

## 2. 我亲自完成了哪项推演或实验

- 案例编号：`deadlock_01`、`unsafe_01`
- 输入与参数：
  - `deadlock_01`：`available = [0,0,0]`，P0 的 `need = [0,1,0]`，当前请求 `[0,1,0]`。
  - `unsafe_01`：`available = [1,1,1]`，P0 的 `need = [2,1,0]`，当前请求 `[1,1,0]`。
- 我手算的步骤：
  1. `EXCEEDS_NEED`：在 `deadlock_01` 让 P0 请求 `[0,2,0]`，`2 > need[B] = 1`，第一步即拒绝，状态不变。
  2. `EXCEEDS_AVAILABLE`：在同一状态让 P0 请求 `[0,1,0]`，满足 need，但 `1 > available[B] = 0`，拒绝，状态不变。
  3. `UNSAFE_AFTER_TRIAL`：在 `unsafe_01` 让 P0 请求 `[1,1,0]`，前两步都通过；试分配后 `available = [0,0,0]`、P0 分配 `[2,1,0]`；三个进程的 need 都有分量大于零，`work = [0,0,0]` 找不到候选，判定不安全，回滚。
- 程序结果：三种拒绝码分别返回，`after` 与 `before` 逐位相同；`UNSAFE_AFTER_TRIAL` 的记录保留 `trial` 供页面展示前后对比。
- 证据位置：`evidence/exports/deadlock_01_20261126.json`、`evidence/exports/unsafe_01_20261126.json`；本报告 3.4。

## 3. 核验后我修正或确认了什么

我的最初判断被修正：被拒绝的请求**不写入** `requests`，因为本模型的 `requests` 表示案例给定的当前阻塞请求，拒绝不应改变状态；只有授予成功时才清除该进程原有的等待记录。三种拒绝必须分开显示：`EXCEEDS_NEED` 是违反最大需求承诺，`EXCEEDS_AVAILABLE` 是当前可用量不足，`UNSAFE_AFTER_TRIAL` 是资源够但试分配后不安全。统一写成「资源不足」会掩盖判定顺序。

我还确认了释放规则：`0 ≤ release ≤ allocation` 才允许；成功后 `allocation` 减少、`available` 增加，并重新执行安全性检查；释放超过持有量时拒绝且状态不变。

## 4. 还有什么不能据此推出

`requests` 在本模型里是预先给定的输入，不是动态等待队列；真实系统的请求排队、唤醒与抢占都没有建模。拒绝不改变状态，是指在我们的离散模型里；真实内核可能在拒绝时记录调度信息。三种拒绝码的优先级固定，但这不表示其他系统也采用同样顺序。

## 6. 现场验收准备

- 如果被要求改一个 `max` 值：调大 `max` 会让 `need` 增大，原本合法的请求更容易命中 `EXCEEDS_NEED`；调小则可能让原本超限的请求变得合法。
- 如果被要求改一个当前请求：在 `deadlock_01` 把 P0 请求改成 `null`，归约会从 P0 推进，随后 P2、P1 完成，死锁解除；这说明死锁判定只看当前请求。
- 如果被要求解释一次拒绝：我会先报拒绝码，再按固定顺序指出卡在哪一步：超过 `need`、超过 `available`，还是试分配后无安全序列。
