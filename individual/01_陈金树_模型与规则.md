## 1. 我最初怎样判断，为什么

做实验前我认为：银行家算法拒绝一次请求，基本就等于系统已经死锁。理由是教材里的例子常把「不安全」和「死锁」放在一起讲，而请求被拒通常发生在资源紧张的时候，直觉上就是进程互相卡住了。我当时的疑问是：如果不安全不等于死锁，那拒绝到底在拒绝什么？

## 2. 我亲自完成了哪项推演或实验

- 案例编号：`unsafe_01`
- 输入与参数：`total = [2,2,2]`、`available = [1,1,1]`；P0 分配 `[1,0,0]`、最大需求 `[3,1,0]`、当前请求 `[1,1,0]`；P1、P2 按案例原值。
- 我手算的步骤：
  1. P0 请求 `[1,1,0]`：`need = [2,1,0]`，请求未超过；`available = [1,1,1]`，请求未超过。
  2. 试分配：`available = [0,0,0]`，P0 分配变为 `[2,1,0]`。
  3. 安全性检查：`work = [0,0,0]`，三个进程的 need 分别为 `[1,0,0]`、`[0,2,0]`、`[0,0,2]`，第一轮没有候选，判定不安全。
  4. 按模型规则回滚，状态逐位恢复为处理前。
  5. 再看实际死锁：P0 请求 `[1,1,0] ≤ [1,1,1]`，可推进；完成后可用量变为 `[2,1,1]`；P1 请求 `[0,1,0]` 可推进；最后 P2 请求 `[0,0,1]` 可推进，归约顺序 `P0 → P1 → P2`，未死锁。
- 程序结果：请求返回 `UNSAFE_AFTER_TRIAL`，`after` 与 `before` 逐位相同；安全性面板显示不安全，死锁面板显示未死锁。
- 证据位置：`evidence/exports/unsafe_01_20261126.json`；本报告 3.3。

## 3. 核验后我修正或确认了什么

我的最初判断被推翻。拒绝只说明「在最大需求假设下，试分配后不存在安全序列」，它使用的是 `need`；死锁判定使用当前实际请求做归约，不看 `max`。同一个 `unsafe_01` 状态，安全性结论是「不安全」，死锁结论是「未死锁」，两者同时成立。这个反例成为我们分栏展示两类判断的直接依据。

## 4. 还有什么不能据此推出

三类案例都是小规模、串行、无抢占的离散状态，不能据此证明「所有不安全状态都不死锁」，也不能外推到真实内核。`max` 是进程声明的上限，不是运行时事实；如果声明失真，安全性判断会偏保守或失真。归约假设进程获得当前请求后能完成，也不预测它之后的新请求。

## 6. 现场验收准备

- 如果被要求改一个 `max` 值：我会把某个进程的 `max` 调大，预期 `need` 增大、安全序列更容易消失；若某次请求原本安全，可能变成 `UNSAFE_AFTER_TRIAL`。
- 如果被要求改一个当前请求：我会在 `deadlock_01` 把 P0 的请求改为 `null`，预期归约从 P0 开始，可用量变为 `[1,0,0]`，随后 P2、P1 依次完成，死锁解除。
- 如果被要求解释一次拒绝：我会先看拒绝码，区分 `EXCEEDS_NEED`（违反最大需求承诺）、`EXCEEDS_AVAILABLE`（当前可用量不足）、`UNSAFE_AFTER_TRIAL`（试分配后无安全序列，已回滚）。
