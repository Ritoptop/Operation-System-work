## 1. 我最初怎样判断，为什么

我最初认为：等待图出现环就可以判定死锁。理由是教材里的单实例资源例子通常用「环」直接得出死锁，画出一条闭环就结束了。我当时的疑问是：如果资源有多个实例，环是否还足够？

## 2. 我亲自完成了哪项推演或实验

- 案例编号：`deadlock_01`，对照组 `unsafe_01`
- 输入与参数：`deadlock_01` 中 `total = available = [0,0,0]` 的初始可用量；P0 分配 `[1,0,0]`、请求 `[0,1,0]`；P1 分配 `[0,1,0]`、请求 `[0,0,1]`；P2 分配 `[0,0,1]`、请求 `[1,0,0]`。
- 我手算的步骤：
  1. 等待边：P0 等 B，B 被 P1 持有 → `P0 → P1`；P1 等 C，C 被 P2 持有 → `P1 → P2`；P2 等 A，A 被 P0 持有 → `P2 → P0`，形成闭环。
  2. 归约：`avail = [0,0,0]`；P0 请求 `[0,1,0]` 不满足，P1 请求 `[0,0,1]` 不满足，P2 请求 `[1,0,0]` 不满足，没有任何可推进进程。
  3. 不动点：三个进程全部 stuck，判定实际死锁。
  4. 对照 `unsafe_01`：`avail = [1,1,1]`，P0 请求 `[1,1,0]` 可满足，归约依次推进 `P0 → P1 → P2`；虽然安全性检查第一个候选都没有，但当前并未死锁。
- 程序结果：`deadlock_01` 的 `deadlocked = true`、`stuck = [P0,P1,P2]`、等待边与手算一致；`unsafe_01` 的 `deadlocked = false`、归约顺序 `P0 → P1 → P2`。
- 证据位置：`evidence/exports/deadlock_01_20261126.json`、`evidence/exports/unsafe_01_20261126.json`；本报告 3.1。

## 3. 核验后我修正或确认了什么

我的最初判断被修正：等待图有环只是死锁的**必要条件**，多实例资源下必须用归约是否停滞来确认。真正的判定规则是：`requests[i] === null` 视为可推进；否则 `request ≤ available` 才可推进；推进后 `available -= request`，进程完成并释放 `allocation + request`；反复到不动点，若仍有非空请求的进程，才是死锁。`deadlock_01` 的环与归约停滞同时成立，才判死锁；`unsafe_01` 有当前请求但可推进，所以不是死锁。

## 4. 还有什么不能据此推出

归约假设「进程获得当前请求后可在有限步内完成并释放全部持有」，不预测它之后是否提出新请求；因此判定的是当前等待，不是未来调度。等待边模型对多实例资源是粗糙的，只能作为解释辅助，不能单独作为判据。案例规模很小，不能证明「有环不一定死锁」之外更强的普遍结论。

## 6. 现场验收准备

- 如果被要求改一个 `max` 值：死锁判定不看 `max`，所以只要 `requests`、`allocation`、`available` 不变，死锁结论不变；这正好用来解释两套判定的输入差异。
- 如果被要求改一个当前请求：在 `deadlock_01` 把 P0 请求改为 `null`，P0 先完成并释放 `[1,0,0]`，`avail` 变为 `[1,0,0]`；P2 请求 `[1,0,0]` 可满足，随后 P1 也可推进，死锁解除。
- 如果被要求解释一次拒绝：拒绝码由请求处理给出；死锁面板只回答「当前是否还有进程能推进」，两者不要混为一谈。
